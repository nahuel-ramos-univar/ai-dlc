# Refine story

## Response shape
Follow the shared [compact response style](../../../references/response-style.md).

## Context retrieval
Use [context retrieval](../../../references/context-retrieval.md). Read selected module context and current contracts before deeper development or QA refinement.

## Input
Accept a Jira key or URL, or an approved local draft, plus `development`, `qa`, or `combined` mode. Read the issue through Jira MCP using the Jira integration contract when available; otherwise require supplied content and mark the result local-only. A missing parent is not the same as missing approval. An approved standalone technical draft does not need an artificial parent or a `/plan-work` handoff. Provide a `/plan-work` handoff before creating a Task or Subtask only when the draft has neither approved business scope nor approved standalone technical scope.

Read the supplied issue, its relevant parent, approved business acceptance criteria, relevant existing subtasks and issue links, and decisions already recorded. Read affected code, contracts, and tests from the repository. Retrieve only comments and linked work relevant to this refinement; do not crawl the whole project. Use context documents to navigate, then verify every implementation claim against current source — a context document is a map, not proof.

Name the business source: the issue whose approved acceptance criteria this technical work implements. A Jira parent is not automatically that source. A Subtask's parent is a Story, Task, or Bug. A Task may sit under an Epic while its business source is a linked Story. Record the source's key and URL and the approved relationship. Do not treat every dependency link as the business source. If more than one linked issue could be the source, ask one focused question. Technical work that starts from an Epic may name that Epic. Approved standalone technical work does not need an invented business parent.

If a required repository or Jira capability is unavailable, state that limitation and separate verified facts from assumptions. Keep drafting the parts that do not depend on the missing capability; do not claim a complete assessment.

Route by the supplied issue's type:

- **Epic** — refine it directly when it supports meaningful technical enablement, dependencies, or decomposition. Do not force the developer through an artificial intermediate Story first. Return unresolved business scope to the Product Owner through `/plan-work` rather than guessing it. Do not parent a Subtask under an Epic.
- **Story** — refine the implementation and validation of its already-approved business outcome.
- **Technical Task** — prefer updating that existing item over creating another one, when the update stays coherent.
- **Bug** — inspect the reproduction, the expected behavior, the available evidence, and what still needs investigation. Do not invent a root cause.

Discover the connected site's actual Jira issue types and hierarchy before proposing a relationship. This plugin's own planning levels (Epic, User Story, Task) are a conceptual model, not Jira's parent rules — see [Jira integration](../../../references/jira-integration.md).

## Workflow
1. Record the issue's current revision, the analyzed Git baseline, affected paths, and local modifications.
2. Confirm each business acceptance criterion stays business-facing before adding technical detail.
3. In development mode, inspect behavior, callers, contracts, dependencies, compatibility, rollback, and risk.
4. In QA mode, map every criterion to positive, negative, boundary, regression, fixture, environment, and automation needs.
5. In combined mode, resolve conflicts between development feasibility and acceptance evidence. The main chat performs this analysis; do not delegate drafting of the refinement to a specialist agent.
6. **Technical discussion and challenge — always runs, at a depth proportional to the change, regardless of the review profile selected in step 9.** Check what applies: existing functionality that could be reused instead of new code, affected contracts and consumers, data changes and compatibility, failure handling, retries, concurrency, and idempotency, security and operational consequences, testing feasibility, and whether a simpler alternative exists. Challenge a material weakness with evidence and a concrete explanation. The developer may accept, rebut, or revise the proposal; revise the recommendation when the developer's evidence is stronger. Do not invent an objection just to satisfy this step — if nothing material turns up, briefly say what was checked and move on. Ask only questions that change scope, implementation, or validation; do not run a generic questionnaire or a fixed number of rounds.
7. Decide the work breakdown. Prefer one coherent technical item when it is sufficient; this is a default, not a hard limit. Split only when justified by independently verifiable outcomes, distinct ownership or permissions, independent deployment or execution, an explicit prerequisite or dependency, or a size that genuinely prevents useful implementation as one item. A change that touches both the database and the frontend does not by itself require separate items. Do not create empty subtasks by convention. If this project has an applicable DevOps-task-split policy — for example a workspace rule that routes IAM, network, or other platform-owned work into a standalone DevOps task — respect it and explain the split in those terms; do not assume every project this skill runs in has that policy, and do not embed it here as a universal rule for every consumer of this plugin.
8. Before independent review, finish the proposed technical items and check existing child and linked items scoped to this issue, so the proposal does not duplicate technical work already captured. This check covers a new item and an update to an existing one.
9. Select fast, standard, or deep review from semantic risk, uncertainty, and blast radius — see [review-profiles.md](references/review-profiles.md). This selection governs only the independent `refinement-reviewer` delegation, never the challenge in step 6. Fast review may skip independent review; say why. Standard and deep review request an independent `refinement-reviewer` assessment through a supported host agent facility, with the original issue, the identified business source, approved business acceptance criteria, the proposed technical item(s), agreed decisions and material rejected alternatives, source references and baseline, and known uncertainty.
10. If independent delegation is unavailable, disclose the limitation. Never present the main chat's own refinement as an independent review. A documented fast skip is complete. When standard or deep review cannot run, required review stays pending. Do not invent a policy exception. If no applicable project policy explicitly permits publishing without that review, keep publication pending. Drafting can continue.
11. Consolidate only relevant reviewer findings with the developer; avoid an open-ended review loop. Resolve blocking findings before publication. If a finding changes approved business scope, provide a `/plan-work` handoff before changing the issue.
12. Before publication, revalidate the recorded baseline — see [modes-and-drift.md](references/modes-and-drift.md). This applies when creating a new technical item and when updating an existing one. Re-read the business source and, when updating, the technical issue. Check the source files, contracts, and dependencies that supported a material decision. Do not rescan the whole repository because an unrelated file changed. A revision change is not by itself a material semantic change. If relevant evidence materially changed, explain the impact, revise the affected proposal, review that affected scope again, and get renewed approval when the authorized change set changed. Route a business-scope change to the Product Owner. If the relevant evidence cannot be re-read, do not claim freshness was verified, and keep the affected publication pending unless an applicable project policy explicitly permits proceeding with that uncertainty disclosed. Do not claim the Jira read and the later write are atomic, and do not invent an optimistic-locking API.
13. If the proposal materially changes after review — scope, approach, affected contracts, work breakdown, or acceptance criteria — review that affected scope again before publication. A formatting-only change does not need a new review.
14. Propose the Jira change set using [technical-task-template.md](references/technical-task-template.md) only when publication is allowed: blocking findings are resolved, and required review is complete, legitimately skipped under fast review, or covered by an explicit alternative the applicable project policy already permits. Developer approval of the payload does not waive required review. The change set is an update to the existing technical issue, a meaningful Subtask under an eligible parent (a Story, a Task, or a Bug — never an Epic), a linked Task or other issue type the target project supports, or more than one item only for a reason recorded in step 7. Never replace business acceptance criteria; the technical content supplements them.

## Approval boundary
Follow the shared [approval-contract.md](../../../references/approval-contract.md). An authorized developer may approve the technical Jira change set for work that stays inside the already-approved business scope, as a single explicit approval of the complete, reviewable change set — not a separate confirmation per field. That approval does not waive required review. A change to business scope, expected behavior, or business acceptance criteria requires Product Owner approval through `/plan-work` before this skill writes it. Completing independent review, or an edit left in a Canvas, is not publication approval by itself. Do not create a PR or a mandatory technical-plan document.

## Output
Follow [canvas review](../../../references/canvas-review.md) for the approval-ready proposal and again after the Jira read-back. Use the host Canvas capability when this host can open one. Otherwise show the same sections in chat and say Canvas is unavailable on this host. A short status with nothing new to show does not need a Canvas.

Return the analyzed baseline, the identified business source, scoped findings with file references, the challenge-and-response from step 6, review readiness, uncertainty, recommended test coverage, and the Jira change set: items to create or update, their actual issue types, parent or link relationships, exact description and field changes, dependencies, and remaining blockers. After an approved write, re-read the affected records and confirm the actual issues, links, relevant fields, and that the technical acceptance criteria were persisted in the acceptance-criteria field or in the approved description section. If they were not, do not declare the handoff complete. Do not claim transactional or idempotent behavior a tool does not document.
